# UE5 专家岗 AI 替代与自进化训练方案

目标：用 AI 自动化 JD 中人类专家的三项职责（评估模型能力 / 编写示例代码 / 制定改进建议），驱动 Qwen 0.8B / 2B / 4B 小模型在 UE5 游戏开发领域持续自改进。

---

## 0. 范围修订（2026-08-06）：本地只做数据侧，训练在公司侧

约束：本地无 Qwen 模型、不做训练。因此执行边界重划为——

**本地可做（本方案全部落地内容）**：
1. 数据集生产流水线（任务+golden+hidden tests+验证器+judge），输出训练交接包
2. 评估体系（eval 集 + runner + 分层评分），可评估**任意**模型（API 调用）
3. 改进建议报告（对任意模型跑 eval → 失败聚类 → 结构化报告，即 JD 职责 3 的交付物）
4. judge 校准（rubric、人工 golden、kappa、honeypot）
5. 真实 UE 验证（DXC/HLSL 编译、IntroToUE Automation Test 无头跑、真实项目任务提取）

**本地不做，交接给公司**：SFT/DPO/RLVR 训练、模型本地推理、自迭代闭环中"重训"环节。
交付物形态 = 数据文件（Alpaca JSONL / DPO pair）+ 评估报告 + 改进建议报告 + 交接 README，与既有 `UE5_Training_MCP`（dataset v2）、`UE5_Training`（QLoRA 栈，Alpaca 格式）管线对接。

## 1. 角色拆解：人类专家 → 自动化闭环

| JD 职责 | 本质 | AI 替代方案 |
|---|---|---|
| 评估模型能力 | 给出**正确的奖励信号** | 分层验证：编译门禁 + embedding 语义检索 → schema 校验 → 执行沙箱 → LLM-judge |
| 编写示例代码 | 提供**优质训练数据** | 强模型（teacher）生成 + 验证器过滤 + judge 分级 |
| 制定改进建议 | 决定**下一轮生成什么数据** | 失败聚类（hard-example mining）→ 定向补数据 |

闭环：**评估 → 找短板 → 针对短板生成数据 → 重训 → 再评估**。人类专家不可替代的部分只剩"选题、定 rubric、判断什么算好"，粒度从逐样本退到逐任务族。

---

## 2. 两件必不可少的事

**事一：可执行验证（奖励信号）**
- LLM-judge 读代码判对错不可靠（尤其 UE API 幻觉），正确性必须靠执行
- 任务设计在"代码相邻层"：UE API stub 编译沙箱（UObject/AActor/UActorComponent 最小桩）、纯数学核、HLSL 数值比对

**事二：失败驱动的数据生成（迭代决策）**
- 每轮：小模型跑 eval 集 → 按域/错误类型聚类失败 → teacher 针对失败簇生成新任务+参考答案 → 过验证 → 过滤进数据集 → 重训
- 聚类结果即"结构化改进建议"的机器版

---

## 3. 正确性模型与沙箱定位（修正版）

**核心论题**：执行沙箱不是"正确性的裁决者"，而是"**规格内正确性的最强可自动化证据**"；意图层必须显式留给 judge + golden，并承认该层信号弱。

### 3.1 正确性拆两层

- **符合规格**：断言覆盖范围内的行为。沙箱可证，但**确定性 ≠ 有效性**——信号只确定地反映"断言写了什么"，断言覆盖度才是有效性的度量。覆盖度外的 bug、UE 版本差异、构建漂移会让信号**稳定地错**，安静毒化 reward。回归护栏必须锚定在"经意图层校准过的 eval 集"上，否则只防掉分、不防分数本来就坏。
- **符合意图**：任务原意是否被还原。"代码能跑、断言全过、但建了个很好的错误东西"是生成式 UE 代码最常见的失败形态，沙箱对此**零覆盖**，只能由 judge + 人工 golden 承担。这层信号弱，是体系的天花板，不是待优化的边角。

### 3.2 经济学论点（替代"规模/稳定"论点）

**沙箱把人类成本从 O(样本) 摊到 O(任务族)**：rubric、断言、golden 每域定义一次，在样本量上摊销。人一直在闭环里，只是粒度退到逐任务族；"无人值守"的正确含义是**样本级无人、任务族级策展**。

### 3.3 最强形态：动态闭环

静态分层只是过滤。完整形态：**失败聚类 → judge 生成/扩充测试 → 沙箱执行 → 挖出新 bug → 变成新数据**。断言覆盖度在轮次间复合增长，确定性信号的有效性被动态提升。只做过滤的沙箱体系只用了一半潜力。

## 4. 分层验证架构

```
L1 编译门禁 + embedding 语义检索  最廉价；拦语法/API 误用（embedding 比对远多于 exact-match）
L2 Schema/预算校验                配置类任务（Niagara 配置、碰撞通道等转 JSON）
L3 执行沙箱                       只对"值得执行"的任务；CPU 纯数学核优先
L4 LLM-judge + 人工 golden        意图层；rubric 每域定义一次，样本上摊销
```

落地纪律：
- **分层份额是实验结论，不是架构设定**：先做小批量试点，实测各层拦截率、执行成本、flakiness，再定任务分布
- L3 优先 CPU 数学核（冲量、PID、剔除数学）；HLSL 数值验证用从 shader 提取的标量数学做软件求值，GPU 不进 CI
- UE 构建脆弱（环境漂移、链接时长）、测试 flakiness 是沙箱规模化的真实敌人，写进成本模型
- 真正没法执行的（整体特效效果）退到 schema+judge，承认该层信号弱，靠失败聚类补

## 5. 三域任务设计与验证

前提：UE 的 .uasset 配置无法直接执行，所有任务设计在"代码相邻层"——HLSL 可编译、数学核可运行、配置转结构化 JSON 可模拟验证。

### 5.1 特效系统（Niagara / 材质 VFX）

| 任务类型 | 验证方式 |
|---|---|
| Niagara 模块 HLSL（curl noise、flipbook、溶解） | DXC 离线编译 + 数值比对（已知输入输出） |
| Niagara 系统配置（生成率/寿命/发射逻辑） | 转 JSON spec → 轻量模拟器：粒子峰值、生命周期曲线、内存预算 |
| 材质函数数学（shockwave、扭曲、边缘光） | 纯数学函数单测 |
| 粒子逻辑（死亡事件、事件互连） | 桩类型 + 逻辑测试 |

judge 维度：GPU vs CPU sim 选型、Data Interface 用法、预算意识。
失败簇预测：HLSL 语法/语义错误、粒子寿命数学错、Data Interface 误用、预算爆炸。
素材：Epic FX 官方示例（引擎内置）、开源 Niagara 插件。

### 5.2 物理系统（Chaos / 刚体 / 载具 / 布料）

| 任务类型 | 验证方式 |
|---|---|
| 数学核（冲量解算、弹簧阻尼、载具轮模型、升力阻力、约束投影） | 纯 C++ + FVector 桩 → 固定步长积分器跑 N 步，断言不变量（无 NaN、能量有界、收敛） |
| 射线/重叠/碰撞通道配置 | Schema 校验 + 规则检查（碰撞矩阵、TickGroup 依赖） |
| 约束设置、睡眠阈值、参数调优 | 规则校验 + 数学边界检查 |
| 布料/流体 | 只验证约束投影数学核，其余转"解释+调参"题走 judge |

失败簇预测：**UE 单位是 cm**（力/质量换算）、冲量符号、质量与速度尺度、睡眠阈值误用、轴约定。
素材：Chaos 文档示例代码、开源载具/布料插件。

### 5.3 渲染管线（Shader / Pass / LOD / 优化）

| 任务类型 | 验证方式 |
|---|---|
| 后处理/自定义光照 HLSL（toon、SSAO 变体、色调映射） | DXC 编译 + 已知输入数值比对（软件求值） |
| 视锥剔除、LOD 选择、mip bias 数学 | 纯数学全可执行（随机数据 + 断言） |
| Render Pass 依赖图（RT 生命周期、异步计算顺序） | 抽象成 DAG → 小型模拟器验证资源生命周期与排序合法性 |
| Nanite/Lumen/VSM 配置 | Schema + 预算数学（内存/流送）+ judge |
| 性能优化题（draw call 合并、GPU 带宽估算） | 估算数学可执行 + judge 工程化分 |

失败簇预测：sRGB vs linear 双伽马、SRV/UAV 生命周期、mip 约定、Pass 顺序。
素材：UE5 官方示例工程、GitHub 开源渲染插件（体积雾、PBR 扩展）。

## 6. 训练与评估

### 6.1 模型尺寸 × 任务粒度

| 模型 | 任务粒度 | 示例 |
|---|---|---|
| 0.8B | 单函数/单表达式 | 修一个 HLSL 函数、算一个冲量 |
| 2B | 单模块 | 一个 Niagara 模块、一个物理约束类 |
| 4B | 单系统协同 | 载具类（轮+悬架+仪表）、Pass 组配置 |

### 6.2 训练流程

1. SFT：teacher 生成、验证器过滤过的原子任务数据
2. DPO：judge 对同一任务的多个解打分，构造偏好对，强化"工程化写法"
3. （可选）执行反馈 RL：沙箱通过/失败做 verifiable reward，对数学核类任务最有效

### 6.3 评估双层

- **硬分数**：执行通过率（分层验证产出，确定性）
- **软分数**：judge 按 rubric 打分（UE 规范/UPROPERTY、可读性、性能、工程化），强模型 + 人工 golden 定期校准（kappa ≥ 0.7），honeypot 抓系统性偏差
- 回归护栏：任何域分数不得掉；eval 集本身经意图层校准

---

## 7. 数据集策略

- **合成数据（训练主体）**：teacher 批量生成"任务+参考实现"→ 验证器过滤 → judge 分级。注意反同质化（改写、混任务模板），防模型塌缩（保留真实数据 ≥10%）
- **真实 UE 项目（eval 集 + 任务素材）**：从开源 UE 项目（Lyra、GitHub 插件/Demo）提取真实任务：改 bug、移植功能、性能改写
- **UE 引擎源码（API 语料）**：抽 API 用法做"API 正确性"语料，也是 embedding 语义检索比对的基础，专治小模型 API 幻觉

## 8. 自迭代机制

```
固定 eval 集 → 当前模型跑 → 失败聚类（按域/错误类型）
     ↑                                  ↓
     └──── 重训 ← 合并过滤后的新数据 ← teacher 定向生成新任务
```

三个关键机制：
1. **hard-example mining**：失败样本转化为新训练数据
2. **数据保鲜**：按比例掺新数据，防灾难性遗忘
3. **回归护栏**：重训后 eval 集分数不得掉（锚定经意图层校准的 eval 集）

失败簇预测表即定向生成地图，与三域一一对应（见第 5 节）。

## 10. 修正版结论

**执行沙箱是规格内正确性的最强可自动化证据，正确性裁决权在 judge + golden，意图层信号弱且必须显式承认；沙箱的价值随测试生成闭环复合增长，而非静态过滤。**
