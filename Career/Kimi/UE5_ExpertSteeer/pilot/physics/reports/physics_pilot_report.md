## 2. 分层验证矩阵（golden + 3 失败解，每任务）

L1 = 导入/语法 + API 表面检查（函数存在、签名参数名与顺序、禁用模式扫描、返回类型冒烟）。
L3 = hidden tests 全跑，容差 1e-4（KINDA_SMALL_NUMBER 级别）。
L4 = judge 由 **agent 扮演**（真实校准需人工 golden + kappa ≥ 0.7，属后续步骤；见 §6）。
墙钟 = 每次验证运行的总墙钟（含解释器进程启动），3 次重复分别列出。

## 4. Flakiness（每解 3 次重复）

- **判定稳定性：36/36 次判定完全稳定**（L1/L3 判定零抖动）。所有测试均为确定性输入 + 纯函数，无随机源（L1 门禁含 `random/IO/eval` 禁用扫描，从源头排除抖动）。
- **墙钟抖动：显著**（64.8–535.2 ms，最大/最小 ≈ 8.3×），来源为 Windows 子进程启动（解释器 + 杀软/调度）。判定不受影响。
- 结论：物理域数学核任务的 flakiness ≈ 0（判定层）；成本模型应取中位数并设预算上限，不做单次测量决策。golden 解重复跑 3 次判定全 PASS。

放行判定说明（构成"仅 L3 可拦"证据）：
- **impulse F3**：float32 降精度是游戏物理中常见的"性能优化"写法，静态读码无法确定其在 1e5 cm/s 量级违反 1e-4 容差（低速下完全无感）。agent-judge 按 rubric 给 正确性 7，加权 6.9 → PASS 放行。
- **spring F1**：位置-速度两种更新次序同为能量有界的辛格式，代码自洽合法；仅精确轨迹断言（t2 单步字面量）能暴露 O(dt) 轨迹偏移。敏感性：若 rubric 严格按 prompt 字面"先 v 后 x"判 API 维度，可改判 FAIL——这正是"静态层信号弱"的实证。

**声明**：judge 由 agent 扮演（单点、无盲测、无 kappa）。真实校准需人工 golden 标注 + 多 judge 一致性（kappa ≥ 0.7），属 Stage 1+ 步骤。计划 §2 的前提"LLM-judge 读代码判对错不可靠"意味着真实部署中 judge 的漏检率只会高于本表（agent 扮演接近理想 judge）。

## 7. 每任务"L3 执行是否必要"结论

定义（README 协议）：**L1+judge 拦不住的错误占比**——播种失败中同时通过 L1 且被 agent-judge 放行、只有 L3 能拦的比例。

| 任务 | L3 拦截 | 仅 L3 可拦 | L3 盲区 | 结论 |
|---|---|---|---|---|
| impulse | 3/3 | 1/3（33%） | 0 | **L3 必要**：float32 精度错误静态零可见性，必须执行 |
| spring | 3/3 | 1/3（33%） | 0 | **L3 必要**：更新次序错误能量有界、读码合法，只有精确轨迹断言可拦；且单位错误 F3 被字面量测试拦下而**能量/收敛不变量放行**——执行层内断言覆盖度也分强弱 |
| wheel | 2/3 | 0 | 1/3（33%） | **L3 与 judge 互补，缺一不可**：L3 确定性拦 2/3；但硬编码解 L3 全过（符合规格但错误），只能靠 judge 意图层 |

**总体结论**：纯 L1+judge（agent 扮演的理想化情况）拦不住 2/9（22%）播种错误；在计划 §2 的"LLM-judge 不可靠"前提下，L1+judge 组合的漏检率只会更高，实测 L3 实际拦截 8/9（89%）。**L3 执行沙箱是必要的**：三个任务中有两个存在仅执行可拦的错误（33%/任务），第三个任务的 L3 拦截率也是 67%；同时 L3 存在 11% 盲区（硬编码/符合规格但错误），judge 不可省。分层份额建议（试点口径）：L3 执行任务占比 ≥ 2/3，judge 全量陪跑用于盲区与工程化评级。

## 8. 次要发现（断言覆盖度）

- **不变量 ≠ 全覆盖**：spring F3（单位错）通过了 200 步能量有界 + 收敛不变量（软 100 倍的弹簧同样"收敛"），靠单步字面量断言（t2/t3）才拦住。→ 断言设计必须"字面量精确轨迹 + 不变量"双轨，只写不变量会漏单位类错误。
- **行为错误可以局部正确**：impulse F1/F2 都通过了分离守卫（t5）与纯切向（t6）用例；wheel F2 通过了输出恰为 0 的用例。→ 单测多样性（边界 + 符号 + 尺度）是拦截率的直接决定因素，支持计划 §3.3"测试覆盖度动态扩充"。
- **精度类错误需要量级刺激**：impulse F3 在常规 100 cm/s 输入下完全正常，只有 1e5 cm/s（UE 高速抛射物常见量级）+ 非整数法线才超容差。→ 测试向量应覆盖 UE 实际量级（cm 尺度大数），这本身是物理域特有要求。

## 9. 局限与后续

- judge 由 agent 扮演：需人工 golden 标注与 kappa ≥ 0.7 校准（Stage 1）。
- 只测了 3 任务 × 3 失败类型；失败簇表其余条目（睡眠阈值误用、轴约定、约束投影）未覆盖，扩量时建议按本协议每任务 4 解续测。
- 未跑 UE 构建（协议边界）；Stage 1 迁移目标是 FVector 桩 → 真 C++ 编译沙箱，届时 L1 应扩展为编译门禁 + embedding 语义检索（§4）。
- 成本优化项：解释器启动占墙钟 >99.9%，进程池/常驻 worker 可把 L3 单解成本降至 <1 ms，flakiness 时间抖动也随之消失。
